# 0. Executive Summary

QuantFoundry V1 要解决的核心问题不是：

> 如何让个人投资者自己学会写量化策略？

而是：

> 如何让一个缺乏专业量化团队的个人投资者，通过自然语言管理一支由 AI Agent 驱动的“虚拟量化研究团队”，让 AI 操作确定性的量化研究工具完成研究、验证、组合和复盘工作？

产品核心关系：

```text
人
│
│ 提出投资问题
│ 审阅关键证据
│ 掌握最终资本权限
▼
Research Director AI
│
├── Factor Scientist
├── Strategy Scientist
├── Portfolio Analyst
├── Red Team Researcher
└── Performance Analyst
        │
        │ Semantic Tools
        ▼
──────────────────────────────
     Deterministic Layer
──────────────────────────────
Data Engine
Factor Engine
Simulation Engine
Portfolio Engine
Validation Engine
Risk Engine
Performance Engine
Paper Execution Engine
Experiment Store
──────────────────────────────
```

核心原则：

> **AI 决定研究什么、如何解释证据、下一步做什么。**

> **软件决定数值是多少、回测发生了什么、规则是否通过。**

V1 不追求真正券商实盘。

V1 必须完整打通：

```text
Natural Language Idea
        ↓
Research
        ↓
Factor Analysis
        ↓
Strategy
        ↓
Fast Backtest
        ↓
Strategy Freeze
        ↓
Independent Validation
        ↓
Red Team
        ↓
Portfolio Analysis
        ↓
Investment Memo
        ↓
Human Approval
        ↓
Paper Trading
        ↓
Performance Review
```

如果这条链能够可靠运行，V1 即证明 QuantFoundry 的核心产品假设成立。

# 1. 产品背景

传统系统化投资研究通常需要多个角色：

- Quant Researcher
- Data Researcher
- Portfolio Manager
- Risk Analyst
- Quant Developer
- Performance Analyst
- Research Director / PM

个人投资者最大的障碍通常不是“没有一个 RSI 回测库”。

真正缺失的是：

```text
有人把模糊投资观点
        ↓
转换成严谨研究问题
        ↓
设计实验
        ↓
理解结果
        ↓
发现过拟合
        ↓
继续设计实验
        ↓
构建组合
        ↓
验证风险
        ↓
形成投资决策
```

大量现有量化框架解决的是：

> **计算问题**

而 QuantFoundry 要解决的是：

> **研究组织问题**

# 2. 市场与技术调研结论

## 2.1 OpenBB

OpenBB 当前的 Open Data Platform（ODP）非常适合成为 QuantFoundry 的数据接入层，而不应成为 QuantFoundry 本身的 UI。

ODP 已经面向 Python、REST API、研究环境和 AI/MCP 场景暴露数据能力。

因此 V1 定位：

```text
OpenBB ODP
=
Data Adapter / Provider Abstraction
```

而不是：

```text
OpenBB Workspace
=
QuantFoundry UI
```

QuantFoundry 应建立自己的产品对象和 UI。

------

## 2.2 vectorbt

vectorbt 非常适合快速研究阶段。

其核心优势是可以大规模运行参数组合、信号和组合模拟，同时支持向量化及 callback/event-driven 类型的模拟。

V1 定位：

```text
vectorbt
=
Fast Simulation Engine
```

主要承担：

- 快速 backtest
- 参数扫描
- 信号比较
- exploratory research

不作为最终严格验证唯一来源。

当前 vectorbt 使用 Apache 2.0 + Commons Clause 的 fair-code 许可，因此如果未来产品商业发行，需要单独完成许可证审查。

------

## 2.3 LEAN

LEAN Engine 本身是开源的事件驱动交易引擎，覆盖 research、backtest 和 live trading，采用 Apache-2.0。

因此 V1 定位：

```text
LEAN
=
Strict Simulation / Validation Adapter
```

需要注意：

LEAN Engine 与 LEAN CLI 不能视为同一个产品授权条件；当前官方 CLI 文档指出使用 CLI 需要 QuantConnect 付费组织成员资格。

因此：

**QuantFoundry V1 不应在架构上硬依赖 LEAN CLI。**

优先研究：

```text
Direct LEAN Engine Integration
        或
Controlled LEAN Container Adapter
```

------

## 2.4 Alphalens-reloaded

Alphalens-reloaded 目前可以直接提供：

- Returns Analysis
- Information Coefficient Analysis
- Turnover Analysis
- Group Analysis

等 Factor Research 能力。

V1 可以复用其算法和输出作为 Factor Engine 的重要基础。

但不得直接把第三方 library 输出当作无法质疑的 truth。

例如当前项目中仍存在关于 long-short spread leverage 语义的公开问题。

因此：

> 所有重要指标必须经过 QuantFoundry 自身测试层封装。

------

## 2.5 Riskfolio-Lib

Riskfolio-Lib 基于 CVXPY，提供多种 portfolio optimization、risk measure 和 risk parity 等组合构建能力。

V1 定位：

```text
Riskfolio-Lib
=
Portfolio Mathematics Backend
```

用户和 Agent 不直接调用 Riskfolio API。

统一由：

```text
Portfolio Engine
```

包装。

------

## 2.6 QuantStats

QuantStats 提供：

- performance statistics
- charts
- drawdown analysis
- HTML tear sheet

等能力。

但其项目当前明确存在部分 trade-level 指标无法仅从 return series 正确计算的问题。

因此 V1 决策：

```text
QuantStats
=
Visualization / Report Helper
```

而不是：

```text
Performance Source of Truth
```

订单级：

- turnover
- slippage
- trades
- holding period
- implementation shortfall

必须由 QuantFoundry 自己从订单和持仓数据计算。

------

## 2.7 LangGraph

LangGraph 当前原生支持：

- durable execution
- persistence
- human-in-the-loop
- interrupt
- subgraph

并明确适合混合 deterministic step 与 LLM-driven step 的 workflow。

因此 V1 推荐：

```text
LangGraph
=
Agent Workflow Runtime
```

V1 Runtime AI 的模型执行统一通过一个远程 Codex logical instance `CODEX-DEFAULT` 提供；LangGraph 保留 workflow/checkpoint/interrupt/subgraph 职责，不再由各 Role 创建或选择独立的内置 Agent/Provider。Remote Codex 的 tool intent 必须回到 QuantFoundry server-side Semantic Tool Policy，不得直接访问业务基础设施。

而不是量化计算平台。

# 3. V1 产品目标

## 3.1 Primary Goal

用户可以输入：

> 帮我研究一下，美股中高质量且有中长期动量的公司是否能长期跑赢标普500。

之后系统能够：

1. 自动转换成研究假设；
2. 判断所需数据；
3. 自动执行 Factor Research；
4. 自动运行实验；
5. 解释结果；
6. 形成 Strategy Candidate；
7. 严格验证；
8. Red Team 主动攻击；
9. 分析加入现有组合后的价值；
10. 形成 Investment Memo；
11. 用户批准；
12. 进入 Paper；
13. 后续自动复盘。

# 6. 产品设计原则

## 6.1 AI First, Notebook Optional

用户默认不接触：

```text

Notebook
vectorbt

```

这些属于实现细节。

------

# 6.2 Progressive Disclosure

默认界面只展示投资决策真正需要的内容。

例如默认显示：

```text
年化收益
最大回撤
Sharpe
换手率
与 Benchmark 比较
```

高级用户展开：

**Advanced Metrics**

才能看到：

- IC IR
- skew
- kurtosis
- tail ratio
- factor loading
- serial correlation

------

# 6.3 Evidence Before Opinion

每个 AI 结论必须能够反向找到：

```text
Conclusion
    ↓
Evidence
    ↓
Experiment
    ↓
Tool Call
    ↓
Dataset
```

------

# 6.4 不提供“AI 信心 87%”

V1 不设计：

```text
AI Confidence = 87%
```

这种带有虚假精确度的指标。

应该展示：

```text
Evidence Status

Strong
Mixed
Weak
Contradictory
Insufficient
```

以及支持理由。

------

# 6.5 不暴露 Chain-of-Thought

Agent Activity 页面展示：

```text
任务
调用工具
获得结果
决策摘要
下一步动作
```

不展示模型内部隐藏 reasoning token 或完整 chain-of-thought。

------

# 6.6 Evidence Foundry 交互方向

QuantFoundry 的目标前端不是通用 AI dashboard，而是 **Evidence Foundry**：一个证据优先、克制、可审计、数据密集但可理解的研究工作台。

所有页面设计必须按以下顺序完成，禁止只换颜色、圆角或卡片：

```text
用户任务与叙事
    ↓
信息架构与决策顺序
    ↓
视觉方向
    ↓
Design Token / Component System
    ↓
响应式布局与完整状态
    ↓
截图、可访问性与发布审查
```

实施前必须先研究 3–5 个同类高质量产品，归档 desktop/mobile 关键截图，并记录可抽象原则、不可复制的品牌资产和对应改造动作。参考只用于抽象信息层级、排版密度、色彩关系、组件模式和交互节奏，不得复制 logo、专属插画、文案、客户、推荐语或虚构指标。

视觉与交互约束：

- Chinese-first typography；数值使用稳定的 tabular numerals；
- 单一克制强调色，风险、证据和生命周期状态使用固定语义色；
- 禁止无业务意义的紫蓝渐变、默认三列卡片、过度大圆角/阴影和 card soup；
- 每页必须明确一个首要问题、关键证据、当前状态、下一步与唯一主 CTA；
- Progressive Disclosure 不得隐藏阻断、风险、数据来源、版本、审批或失败原因；
- 动效只用于状态变化与空间关系，支持 `prefers-reduced-motion`。

------

# 6.7 响应式与可访问性

V1 不建设原生移动 App，但响应式 Web 必须从 390px 起可用。目标验收 viewport 至少覆盖 390、768、1280、1440px；不得出现页面级横向滚动、不可达主 CTA、被遮挡 dialog/drawer、文本或图表溢出。复杂图表在窄屏可切换为摘要/表格，但不得丢失风险、证据或审批语义。

目标为 WCAG 2.2 AA：全键盘可达、可见焦点、语义化名称、对比度、错误关联、非颜色唯一表达、reduced motion。Loading、Empty、Error、Success、Active、Disabled、Dirty、Validation、Conflict、Stale、Degraded、Permission、Partial data 均必须有规范状态，不得只实现桌面成功态。

------

# 7. Human Principal 与访问边界

V1 只有一个固定 human principal。`Owner / CIO` 仅是产品展示名称，不是可分配角色，也不产生 user、member、tenant 或 RBAC 模型。

# Owner / CIO

系统必须满足：

- 不存在 email/password 登录；
- 不存在 user list、invite、member、role assignment 或 permission matrix；
- 不存在 workspace create/list/switch；
- 一个内部 singleton namespace 只用于数据归属、审计、幂等和存量兼容，不能由客户端选择、创建或枚举；
- 多个通用密钥均映射到同一个 human principal，权限完全相同；
- Agent/System actor 仍作为审计 actor type，与 human principal 区分，但不构成人类用户。

权限：

- 创建研究
- 修改 Research Brief
- 查看所有结果
- 查看审计
- 管理 Agent
- 管理 Data Provider
- 修改 Research Policy
- 批准 Holdout
- 批准 Paper
- 停止 Paper

# 12.6 页面 P-01 — Login / Recovery Access

Route：

```text
/login
```

页面目标：使用任一有效通用密钥换取短期 HttpOnly session。页面只接受通用密钥，不显示 email、username、password、signup、invite、workspace 或 role 入口。

登录流程：

```text
输入通用密钥
    ↓
Bootstrap Control DB 校验 verifier / status / expiry
    ↓
建立短期 HttpOnly + Secure + SameSite session
    ↓
Domain DB healthy  → 进入目标页面或 Overview
Domain DB degraded → 进入受限 Recovery Settings
```

浏览器不得把通用密钥写入 localStorage、sessionStorage、IndexedDB、cookie、URL、telemetry 或普通 log；登录完成或失败后立即清空输入值。错误不得泄露 key ID、label、是否曾存在或 verifier 细节，统一表达为无效、已撤销或已过期的不可区分认证失败。

固定嵌入式 Bootstrap Control DB 独立保存 access-key verifier、session、配置目录/值/revision、加密后的 Domain PostgreSQL connection 及恢复状态。Domain DB 不可用时，有效通用密钥仍必须能够登录，但仅可访问 Recovery Settings、数据库连接测试/激活、Bootstrap health、logout 和必要的恢复审计；Research、Paper、Approval、Agent run 等 domain surface 必须 fail closed。

首次安装且不存在任何有效密钥时，安装流程必须通过受信任的本机安装通道生成初始通用密钥，明文只展示一次并立即只以 verifier 入 Bootstrap Control DB；不得开放可被远端抢占的匿名“创建首个密钥”页面。该安装通道不是普通配置来源。

本节为目标产品语义。登录、session、key lifecycle 与 recovery 的 canonical operations、errors 和 schema 必须由 §79 D1 machine contract rewrite 定义；D1 前不得基于本节猜测 endpoint 或实现。

```text
Bootstrap Control DB
├── access-key verifier / label / lifecycle
├── short-lived session / revocation
├── configuration catalog / ordinary mutable values / global revision
├── exact active refs to immutable/versioned Domain objects
├── encrypted Domain PostgreSQL connection candidates + active binding
├── bootstrap health / recovery state
└── configuration and access audit

Domain PostgreSQL
├── research/risk policy versions
├── cost model versions
├── other immutable/versioned configuration objects requiring domain lineage
└── all research domain data
```

每个配置项必须有唯一 catalog entry，并声明：key、category、value kind/storage authority、type、default、validation、secret/write-only、mutable、restart/reload requirement、dependency、effective value、revision、updated_at、audit locator。所有普通 mutable value、global revision/active pointer 与 effective selection 都在 Bootstrap Control DB；只有需要 domain lineage 的 immutable/versioned object 内容存在 Domain DB，Control DB active revision 保存其 exact object/revision ref。同一 value 不得在两库双写或 fallback。禁止 YAML、TOML、JSON、`.env`、环境变量、命令行参数、browser storage 或进程内默认覆盖作为普通配置来源或 fallback。

唯一例外是解密 Bootstrap Control DB 中密文所需的加密 root。它只允许来自 OS keychain、TPM 或 external secret injection，是不可消除的 root-of-trust，不是配置项；不得通过 Settings 展示、导出或覆盖，也不得存入仓库、配置文件或同一数据库。

# Database

该页面在 Domain DB healthy、degraded 或 unavailable 时均由 Bootstrap Control DB 提供。Domain PostgreSQL connection 是加密写入 Bootstrap Control DB 的 write-only secret，不得回显 password/token；页面只显示非秘密摘要、active revision、last validated、health 与失败分类。

修改采用双阶段，不得边输入边切换：

```text
Stage Candidate
    ↓
Test Connection
    ├── network/auth/TLS/version/schema/migration check FAIL
    │      → 保留当前 active binding；candidate 可修改或丢弃
    └── VALIDATED
           ↓
       Review Impact
           ↓
       Activate with revision check
           ↓
       Bootstrap Control DB 原子切换 active binding
           ↓
       Domain health recheck
```

Test 不得激活或覆盖当前连接；Activate 必须使用 candidate revision/ETag，冲突时要求重新读取。激活失败时保留 last-known-good binding，不得写一半。Domain DB down 的 Recovery Settings 只允许编辑、测试、激活连接和执行必要恢复动作；不得绕过 schema/migration compatibility、Research Integrity 或 secret isolation。

Database locator、credential、TLS material、pool/runtime 参数等只要是可变值，均必须按上述流程入 Bootstrap Control DB。不得从环境变量、`.env`、Compose YAML 或命令行 fallback。加密 root 仍遵循本节前述不可消除 root-of-trust 例外。

# Disabled / Permission

Disabled control 必须说明前置条件、缺失 capability、不可关闭的安全规则或当前恢复态边界。固定 human principal 不存在 RBAC permission denial；`403` 只可表达 server-side approval、frozen-state、risk、tool policy 等领域规则，不能伪装不存在的用户角色差异。

------

# Dirty / Validation

未保存 draft 必须有明确 dirty indicator、离开保护和逐字段 validation。Secret 字段不得因 validation、重渲染、resync 或错误恢复而回显。浏览器刷新后不得从 browser storage 恢复 secret draft。

------

# Conflict / Stale

ETag/revision conflict 必须保留当前 route、scroll、Tab 与非秘密 draft，展示服务器当前 revision 和用户变更摘要，要求 reload/重新应用；禁止静默覆盖或整页清空。持续 event/schema incompatibility 进入 degraded 状态，不无限重连。

------

# Degraded / Partial / Recovery

Domain DB、Provider、Agent Runtime、Worker 或 Scheduler 降级必须指出受影响能力与仍可安全执行的动作。Domain DB unavailable 时只允许 Bootstrap Control DB 提供的 Login、Recovery Settings、health、必要恢复审计和 logout；任何 domain object 读取/写入均 fail closed。Partial data 必须标出缺失范围、时间与来源，不能以 0、空图或缓存值伪装完整。

------

# Visual / Responsive / Accessibility QA

每个受影响页面必须以真实浏览器记录 390、768、1280、1440px 的关键截图，覆盖 success 及适用的 loading、empty、error、degraded、dirty/conflict。验收至少检查：无页面级横向滚动、文本/图表/dialog 不溢出、CTA 可见、键盘可达、焦点可见、语义名称、对比度、reduced motion、真实文案与无敏感信息。

视觉 baseline 必须来自可信 Git ancestor 或人工批准的 bootstrap candidate；被测 revision 不得自批 baseline。截图 QA、自动可访问性和独立人工审查必须同时满足，不能以单一模型自评替代。

## Event refresh contract

R2 SSE 只接受 canonical generated `EventType` 的 31 个精确小写成员；`SseEnvelope`、`EventPayload`、`EventWaitingOn` 均按 closed schema 解码，`EventWaitingOn` 仅为 `{type:'JOB',job_id}`。不得维护前端自定义 event union、开放 payload map 或把 notification 当对象 truth。

Event/Audit locator 只有 21 个 closed branch：`job/research/conclusion/experiment/factor/strategy_version/validation/approval/paper/paper_run/review/capability/snapshot/agent_run/tool_call/memo/notification/settings/provider_connection/agent_config/event_stream`。其中当前 14 个 producer branch 为 `job/research/experiment/factor/strategy_version/validation/approval/snapshot/agent_run/tool_call/memo/settings/provider_connection/agent_config`；`event_stream` 由 replay/resync 合成；`conclusion/paper/paper_run/review/capability/notification` 是已生效 EventType 所需的正式目录 branch，不因 R2 无当前 writer/page 而降级为自由 string。

31 个 EventType 必须由 canonical generated pair rules 精确选择 branch：

```text
job.updated→job
research.created|research.updated→research; research.conclusion.created→conclusion
experiment.created|experiment.updated→experiment; factor.updated→factor
strategy.created|strategy.updated→strategy_version
validation.created|validation.updated|validation.holdout.updated→validation
approval.created|approval.updated→approval
paper.created|paper.updated→paper; paper.run.updated→paper_run
review.created|review.updated→review
data.provider.updated→provider_connection; data.capability.updated→capability; data.quality.updated→snapshot
agent.run.updated→agent_run; tool.call.updated→tool_call
memo.created|memo.updated→memo; setup.completed→settings
notification.created→notification; notification.updated→agent_config
system.health.updated|system.resync_required→event_stream
```

`strategy_version` 必须携带 `STRAT-` aggregate ID + non-null `object_version>=1` + non-null `object_revision>=1`，SSE adapter 禁止把持久化 version 补成 null。`settings` 只允许 `SETTINGS-DEFAULT`；`provider_connection` 只允许 lowercase UUIDv4；`agent_config` 只允许六个 canonical role key；这三者及 `event_stream` 均要求 `object_version=null, object_revision>=1`，`event_stream.object_id` 是当前 envelope `EVT-` ID。未知 branch、EventType→branch mismatch、ID grammar mismatch 或特殊字段缺失均整条 fail closed，进入 `system.resync_required` 的 query-level refetch，不猜 current version。

SSE connection 建立时从 authenticated server context 冻结内部 singleton `workspace_id`；`sequence` cursor、`Last-Event-ID` replay、at-least-once dedupe 与 resync watermark 都只在该 singleton namespace 内有意义。客户端不得通过 query/body/header 选择 namespace；存量非 singleton cursor、event cache 或 dedupe state 不得复用。

各 P0 surface 只做 query-level invalidation/refetch：P00 由 `setup.completed`、`data.provider.updated`、`data.capability.updated`、`data.quality.updated` 刷新 Setup status/capabilities；P01 的相关事件刷新 Overview；P04 由 `research.created`、`research.updated`、`research.conclusion.created`、`experiment.created`、`experiment.updated`、`factor.updated` 与相关 `agent.run.updated` 刷新 Research list/detail；P05 的 `experiment.created`、`experiment.updated` 刷新 Experiment detail 与所属 Research；P09 的 `strategy.created`、`strategy.updated` 刷新 current/resolved version；P11 的 `validation.created`、`validation.updated`、`validation.holdout.updated` 刷新 Validation/Holdout gate，LOCKED 时禁止预取 result；P14 的 `approval.created`、`approval.updated` 刷新 list/detail；P15 的 `memo.created`、`memo.updated` 刷新 memo；`job.updated` 仅刷新对应 Job/已验证 owning object；`tool.call.updated` 仅在 `tool_call_id` 已知且 Tool Call detail query 已 active 时刷新该 detail，可同时刷新现有 Overview 聚合，不枚举 current Tool Call、不对未知 ID 猜测 query；`system.health.updated` 刷新 System Health/Overview。Paper/Review/Notification event 虽在 allowlist，R2 只可刷新现有 Overview，不得因此调用 future-staged endpoint。

未知 future member、大小写漂移、非 `schema_version=1`、任一 envelope/payload/waiting-on extra field 或非法 waiting-on shape 均整条 fail closed：不 merge/cache/toast，进入与 `system.resync_required` 相同的相关 active query resync/refetch。持续版本不兼容须显示 degraded/incompatible，不得无限重连。`validation.holdout.updated` 禁止携带结果值、metric、chart point、credential 或 raw tool/model payload；发现即按泄漏 fail closed，任何 UI/缓存/telemetry detail 不得保留。resync 不重挂 App，不清 route/Tab/scroll/未提交 draft，也不全清 immutable cache。

## 52.1 P0 日调度可执行契约

本节是 Paper daily scheduler 的产品级权威契约；不新增 HTTP API，也不改变当前 canonical OpenAPI 的 `P0_EXECUTABLE_R2` 范围。

调度配置唯一从 `paper_deployments.execution_assumption` 读取。该对象必须是 deployment 创建/更新时已校验并冻结在该 revision 的 closed object，至少包含：

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `schedule_timezone` | IANA timezone string | 计算业务 `trading_date` 的唯一时区；禁止使用 scheduler host timezone。 |
| `daily_due_time` | `HH:MM` 24-hour local time | 每个交易日最早允许创建/唤醒日跑的本地 due-time；精确到分钟。 |
| `trading_calendar` | nullable string | 已配置时为 deployment 绑定、版本可追溯的交易日历标识；未配置时使用 `WEEKDAY_ONLY`。 |

`execution_assumption` 的其他已定义模拟执行字段继续有效，但不得承载第二套 due-time、timezone 或日历语义。缺少、无效或互相矛盾的上述字段时 deployment 不可被 scheduler 执行，必须 fail closed，记录可审计配置错误；不得回退到服务器本地时区、隐式 00:00 或“每天都交易”。

调度器的所有时钟比较、lease、retry 和持久化时间戳均使用 UTC；仅由 `schedule_timezone` 将当前 UTC 时刻映射为业务本地日期和 due-time 判断。`trading_date` 是该业务本地日期的 `date`，不是 UTC 日期。

交易日由绑定的 `trading_calendar` 判定；周末、日历声明的节假日和闭市日都不是 trading date，不能创建 `PaperDailyRun`。`trading_calendar=null` 时唯一允许的默认是 `WEEKDAY_ONLY`：周一至周五为交易日、周六日为非交易日，且不推断法定节假日。日历不可用、版本不明或无法判定日期时必须 fail closed，不创建订单。

## 52.2 P0 触发、补跑与恢复

每次 scheduler wake-up 必须先取得同 workspace、同 deployment 的 `paper_scheduler_states`；缺行、未知 `scheduler_status`、不满足 watermark 不变量或与 deployment lifecycle 不一致时必须 fail closed，并记录可审计的拒绝决定。只有 deployment 与 scheduler state 都为 `ACTIVE` 时才评估一个目标日。候选日的 local due instant 必须严格晚于该 state 的 `resume_watermark_utc`；当前本地交易日已到 due-time 时为该日，否则为最近一个已到 due-time、尚无完成终态且晚于 watermark 的交易日。补跑窗口最多一个 trading date，且只允许最近一个未完成交易日；禁止扫描历史日期、跨多个交易日补跑或因长期停机无限 replay。

`PAUSED` 或 `DISABLED` state 期间不得创建、取得或 enqueue `PaperDailyRun`，且不计算、累积或事后扫描 suppression interval 的 debt。恢复为 `ACTIVE` 必须在同一 transaction 写入新的 `resume_watermark_utc=transition_occurred_at`；因此恢复时点之前（包括恢复日已经到期的 due instant）的日期均不可补跑。恢复后最多只可处理 watermark 之后最近一个未完成交易日。`PENDING`、`FAILED` 或未知 deployment lifecycle 也不得执行；历史 `STOPPED` 是迁移输入，不再是正式 lifecycle 值，必须显式规范化为 `DISABLED`。

候选日以 `(workspace_id, paper_id, trading_date)` 创建或取得唯一 `PaperDailyRun`；并发 scheduler、重复 wake-up、重启或人工重复投递都必须取得同一 run，绝不创建第二个 run、Job、订单、Audit 或 Domain Event 链。已 `COMPLETED` 或 `BLOCKED` 的 run 是该日终态，不重跑；`FAILED` 只可按下述受控恢复处理，不能由新日期触发覆盖。

一个 runner 必须以持久化 lease 独占 `QUEUED`/`RUNNING` run；lease holder 定期 heartbeat，且仅 holder 可写终态。lease 到期后，另一个 runner 必须先原子取得 lease 再恢复。进程崩溃或 lease 丢失时：尚未产生订单的安全阶段可在同一 idempotency key 上重试；订单/成交等 side effect 的提交结果无法确定时必须将该 run 置为 `FAILED`、停止后续执行并要求人工 review，禁止猜测或自动重放。retry 只针对同一 run，必须有限次、可观测且记录 attempt/lease-owner/失败原因；耗尽后为 `FAILED`。

`BLOCKED` 表示 data-quality、数据新鲜度、版本或 risk gate 明确拒绝，当日不得有任何订单；`FAILED` 表示基础设施、执行或恢复不确定性失败，亦不得继续产生订单。scheduler state initialize/pause/disable/resume 与 run 创建、lease 取得/失去、retry、gate block、完成和失败/恢复决定必须原子写入 append-only Audit 和 durable Domain Event，但 evidence 载体按 §52.3 严格分流。state transition 写入现有 Audit `summary` 的 `paper_scheduler_state_evidence.v1` structured detail，不创建 Job 或 Artifact；execution transition 写入 Backend §23.4.1 的 `paper_scheduler_evidence.v1` Artifact，并由 Audit `detail_artifact_id` 关联。state transaction 只可发既有 closed `paper.updated`（如同一 transaction 已有合法 Job 更新，才可另发既有 `job.updated`）；不得借 state transition 发 `paper.run.updated`，更不得在 payload 中加入 state/evidence detail。结构化日志/metrics 必须可按 Audit/Job/Run locator 关联，作为 P0 验收证据。

## 52.3 P0 内部 Scheduler Evidence 边界

Evidence boundary is deliberately split because `artifacts.job_id` is non-null: execution evidence only is the immutable, workspace-scoped `paper_scheduler_evidence.v1` JSON Artifact. It must bind one `PAPER_DAILY_RUN` execution Job and is linked by the execution Audit's `detail_artifact_id`; no empty, arbitrary, or state-only Artifact may satisfy this rule. It is not a public API or SSE payload. Execution evidence fixes `paper_run_id`, `trading_date`, natural idempotency locator, transition/state, `job_id`, attempt, lease owner/expiry/fencing token, UTC timestamps, `schedule_timezone`, `daily_due_time`, calendar identifier/version or `WEEKDAY_ONLY`, side-effect certainty, and failure/review decision.

Scheduler state evidence never creates a Job or Artifact. It is the append-only, singleton-namespace-scoped `paper_scheduler_state_evidence.v1` closed JSON detail in the existing same-transaction `audit_events.summary` field (field schema is Backend §14.45); its `detail_artifact_id` is NULL. It contains `state_transition_id`, legacy field `workspace_id` fixed to the singleton namespace, `paper_id`, `from_state`, `to_state`, `effective_at_utc`, `suppressed_since_utc`, `resume_watermark_utc`, `initialization_utc`, `revision`, `reason_code`, `actor`, `system`, and `commit_build_locator`. Audit is queryable only within the authenticated session + singleton namespace by paper locator/action/time/transition ID; it is not exposed in SSE. The state row update, its Audit detail, and its closed `paper.updated` Domain Event commit atomically or all roll back.

For execution, the natural-key create-or-get, run/Job state, evidence Artifact metadata, Audit and Domain Event must commit in one business transaction; Artifact blob finalization follows Backend §12.6 and failure leaves no formal ref. `FAILED` uncertain side effect records `review_required=true` and forbids automatic replay; safe pre-order retry stays on the same run/Job. Audit lookup begins with authenticated session + singleton namespace and `paper_run_id`, `job_id`, or `trading_date`; Artifact ID, hash, sequence and any locator are never probes for存量非 singleton namespace。

# 59. Security

V1 即使只有一个固定 human principal，也必须：

- Credentials encrypted at rest
- Secret 不进入普通 log
- Provider/API credential 不返回 frontend
- 通用密钥明文只在 Create/Rotate 后一次性返回，随后永不可读
- Access-key verifier 与 session 只存在 Bootstrap Control DB
- Agent 看不到不需要的 secret
- Tool permission server-side enforcement
- Approval server-side enforcement
- Audit immutable by default

## 59.1 Access key 与 session 安全

通用密钥必须是高熵随机 secret；多个密钥权限完全相同，不得成为隐式 RBAC。数据库只保存 verifier 和非秘密 metadata，比较必须抗时序泄漏。明文禁止进入配置文件、Domain DB、browser storage、URL、Audit/Event、普通 log、telemetry、backup manifest 或 Agent context。

Create/Rotate 仅在成功事务后一次性展示明文。Revoke/Expire 必须撤销派生 session；最后一个有效密钥不可撤销、过期或被 rotation workflow 提前失效。Session 必须短期、HttpOnly、Secure、SameSite，服务端可撤销；session cookie 不是可导出的长期 API token。

Bootstrap Control DB unavailable、加密 root unavailable、verifier 状态未知或 session revocation 无法确认时，认证一律 fail closed。Domain DB unavailable 不影响 Bootstrap authentication，但成功登录后只能进入 §12.6 定义的 Recovery Settings allowlist。

## 59.2 Singleton namespace resource boundary

本节取代此前把 workspace 当作可存在多个实例的产品语义。V1 只允许一个 server-created、server-trusted internal singleton namespace；它只为数据归属、FK、lineage、审计、event ordering、幂等和存量迁移兼容存在，不是 user、tenant 或 workspace 产品能力。客户端不得通过 route、query、body、header、token claim 或 UI 创建、列举、切换或选择 namespace。

在 D1/schema migration 完成前，现有 `workspace_id` 字段继续承载该 singleton namespace。Research、Experiment、Strategy/version、Validation/Holdout、Approval、Memo/Paper、Agent Run、Tool Call、Job、Event、Audit、Artifact、Provenance、Policy/Cost/Provider 等内部解析仍必须使用 server-injected singleton ID + public/internal resource ID，不能只凭对象 ID。任何非 singleton、缺失、冲突或客户端提供的 namespace 值均 fail closed；不得据此恢复多 workspace 能力。

Public semantic ID 使用高熵、global unique 标识，只用于冲突防护与追踪，绝不是 bearer、share secret 或 authorization capability。合法 ID 仍必须在认证 session + singleton namespace 内解析；随机不存在、非 singleton 存量或非法 scope 均呈现不可区分的 `404 RESOURCE_NOT_FOUND`，不得通过 403、响应时间、ETag/revision、列表计数、lock 结果、error context、log/SSE/Audit detail 泄露存在性。

自然键与版本键在 schema migration 前继续带 singleton namespace 前缀，包括 settings alias、provider/catalog key、policy/cost family version、Strategy/Factor version、Paper trading date 等。Agent config 在现有 schema 中仍是 `(workspace_id, role_key)` mutable aggregate，但 `workspace_id` 只能等于 singleton ID；不得测试、文档化或实现“相同 role 在不同 workspace”产品行为。

所有内部 FK、lineage、approval subject、Job dependency、Agent root/parent run、Tool/Artifact/Provenance ref 与 checkpoint resume/handoff 都必须验证 singleton invariant。非 singleton ref 必须 fail closed；不能从 checkpoint thread/public ID 反向恢复其他 namespace 的 Run。

`snapshot_partitions` 是没有独立 `workspace_id` 的 immutable child，ownership 只能通过不可变 `snapshot_id` 父链解析到 singleton Snapshot。产品不提供 partition 独立列表、deep link、existence probe 或授权入口；partition/artifact 必须先通过 authenticated session + singleton parent Snapshot 授权。

`domain_events.sequence`、SSE replay cursor、`audit_events.sequence` 与 `prev_event_hash → event_hash` 链在迁移前继续以 singleton namespace 分区。Activity/Audit 只展示该 singleton 的活动；`actor_id` 对 human action 固定映射到唯一 human principal，并额外记录非秘密 credential locator 以区分使用的通用密钥，绝不记录密钥本身。Agent/System action 继续使用独立 actor type。

## 59.3 Public semantic ID exact contract

34 类 public semantic ID 的唯一合法语法为 `PREFIX-` + 以下二者之一：

```text
ULID   = [0-7][0-9A-HJKMNP-TV-Z]{25}  # uppercase canonical Crockford
UUIDv4 = [0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}
```

机器事实源只认 canonical OpenAPI public-ID schemas/policy 与 generated `ObjectRef` conditional；下列 prefix 是产品可读同步视图，不得用于手写 client/server regex 或 prefix map。

Canonical prefixes：

```text
RP RISK COST CRED CAP DSSET DS DQ DQI RSCH EVID CONC EXP FAC STRAT VAL HOLD
RT PORT MEMO APR PAPER PRUN PORD PFILL REV ARUN TCALL JOB EVT AUD ART NOTIF PROV
```

禁止短序号、slug、lowercase ULID、含 `I/L/O/U` 的非 Crockford 字符、ULID 首字符 `8..Z`、uppercase/mixed UUID、非 v4/wrong-variant UUID、任意 suffix、trim、case-fold 或静默截断。Investment Memo prefix 必须是 `MEMO`，`MEM` 永远非法；Holdout exposure 必须是 `HOLD`。`DSSET-` UUIDv4 总长度为 42，storage/schema/route 不得按旧长度截断。

`ObjectRef.type` 是 prefix selector：每个 type 只能搭配 canonical 对应 prefix；type-prefix mismatch、未知 type/prefix 或非法 ID 整体 fail closed。`SETTINGS-DEFAULT`、opaque connection/internal UUID、`role_key`、provider/catalog key、`capability_key`、version/revision/hash/request/build/attention/finding/chart/series ID 不属于这 34 类，不得套 public semantic ID 规则。

上述 grammar 只决定 locator validity；解析/授权仍必须使用 §59.1 的有效 session 与 §59.2 的 singleton namespace boundary。

# 76. 最终产品定义

QuantFoundry V1 不是：

> 一个带 ChatGPT 的回测软件。

也不是：

> 一个会自动生成策略的 AI。

它应该被定义为：

> **一个由 AI Research Team 操作、由确定性 Quant Engines 提供计算与验证、由用户掌握最终决策权的个人系统化投资研究工作台。**

V1 真正需要验证的假设只有一个：

> **在不给普通投资者强加专业量化操作复杂度的前提下，AI Agent 是否能够以足够严谨、可审计和可复现的方式，承担过去需要专业量化研究人员完成的大部分研究操作。**

如果答案是 Yes，之后增加：

```text

More Data

```

只是扩展问题。

如果这个核心 workflow 没有做好，再多指标、图表、因子和券商接口都没有意义。

# 78. Singleton Access / DB Configuration Migration

该迁移是显式 breaking migration，不保留 legacy user auth 与通用密钥 auth 的长期双轨。

迁移前必须：

1. 对现有 human/user、role、workspace/namespace、session、配置来源、credential、Domain DB connection 和数据归属做只读 inventory；
2. 创建并校验可恢复 backup，记录 schema/version/checksum；
3. 证明数据库至多存在一个应保留的人类主体和一个应保留 namespace；
4. 枚举 YAML/TOML/JSON/`.env`、环境变量、命令行和隐式默认中的普通配置值及其当前 effective source；
5. 完成 D1 machine contract rewrite 与 schema/migration authority，不得先运行数据迁移。

迁移规则：

- 新安装创建唯一 human principal 与 singleton namespace；
- 存量恰有一个主体/namespace 时映射到 singleton invariant，保留所有 domain lineage、Audit 与 immutable object binding；
- 存量存在多个主体或 namespace 时 fail closed，输出不含 secret 的冲突清单并要求显式选择/导出；禁止自动合并、猜 owner 或静默丢弃；
- 旧 email/password/role/session 不转换为通用密钥；cutover 时撤销所有 legacy session，并通过受信任安装通道创建首个通用密钥；
- 普通 mutable 配置只允许一次性、幂等导入 Bootstrap Control DB；只有可证明的 immutable/versioned Domain object content 导入 Domain DB，并在 Control DB active revision 中保存 exact object/revision ref。目标已有非等价值时停止，不以文件、环境或时间戳猜优先级；
- Domain PostgreSQL connection 作为 write-only secret 加密写入 Bootstrap Control DB，并完成 Stage → Test → Activate；测试或激活失败保留 last-known-good；
- 导入成功后移除所有普通配置 file/env/CLI read path 与 fallback；重启、Domain DB outage 和 restore 后仍不得回退；
- 加密 root 仅通过 OS keychain、TPM 或 external secret injection 注入，不进入迁移 payload 或 backup；
- rollback 只允许恢复经验证的完整 backup，不得在部分迁移后同时开放两套 auth/config truth。

迁移完成状态必须绑定 commit、Alembic/schema revision、Bootstrap/Domain DB fingerprint、singleton invariant report、config coverage report、secret scan、legacy auth/file-fallback negative report 和独立 Test/Review evidence。

# 79. D1 Machine Contract Rewrite 与目标验收

本 PRD 当前只完成产品目标规范。canonical OpenAPI 仍是当前 45-operation baseline；schema、generated clients 和正式测试 exact counts 也尚未为 Login、key/session、Bootstrap Control DB、Settings-only writes、Domain DB recovery 更新。**不得从本 PRD 推导、猜测或伪造新 operation/schema/test count。**

D1 是相关代码、migration、fixture、generated client 与测试修改的前置 blocker。D1 必须原子同步 canonical OpenAPI breaking revision、目标 exact operation set、Problem Details、schema/Alembic authority、配置 catalog/storage ownership、迁移/弃用策略、generated consumer、UI/前端/后端/Agent/测试正式事实源、Repository Governance 与既有八项 P0 registry closure criteria。D1 前 current baseline 继续用于现状验证；D1 后以更新后的 canonical machine source 为唯一目标 count，不以 `P0-CONTRACT-OPENAPI-45` ID 中的历史数字判断。

目标独立验收至少覆盖：

### 79.1 Access

- 任意两个等权有效通用密钥均可换取同一 human principal 的短期 HttpOnly session；
- 不存在 email/password、user list、invite、RBAC、workspace create/list/switch surface 或 contract；
- key plaintext 只在 Create/Rotate 后展示一次，DB/backup/log/Audit/Event/browser storage 均无明文；
- Revoke/Expire 撤销派生 session，最后一个有效密钥不可撤销或失效；
- invalid/revoked/expired/unknown key 对外错误不可区分，不泄露存在性。

### 79.2 Settings 与数据库

- 所有可变配置 producer 逐项映射到一个 catalog entry、一个 Control DB mutable-value authority（或一个 immutable/versioned Domain object content authority + Control DB exact active ref）和 Settings 中唯一写 surface；
- Data Center、Agent Center 与其他页面无第二个写入口；
- YAML/TOML/JSON/`.env`、环境变量、CLI、browser storage 和隐式默认没有普通配置 read/write/fallback；
- provider/domain secret 加密且 write-only，root-of-trust 只来自允许的外部机制；
- Domain DB connection 的 Test 不激活，Activate revision-protected 且失败保留 last-known-good；
- Domain DB unavailable 时仍可登录并进入受限 Recovery Settings，所有 domain operation fail closed；
- restart、backup/restore 与 Domain DB outage 后配置 effective value/revision 一致且可审计。

### 79.3 Migration

- 单主体/namespace 数据完整迁移且 lineage/Audit 不变；
- 多主体/namespace 输入 fail closed，无自动合并或数据丢失；
- legacy session/auth 与普通配置 fallback 全部不可达；
- populated PostgreSQL roundtrip、rollback/upgrade、Bootstrap recovery 与 restore evidence 完整。

### 79.4 Evidence Foundry UX

- Login、Recovery Settings、Access Keys、Domain Database、Global Shell 与核心业务页遵循 Evidence Foundry 信息层级和同一 design system；
- 390/768/1280/1440px 无页面级横向滚动、文本/图表/dialog 溢出或不可达主 CTA；
- loading/empty/error/success/active/disabled/dirty/validation/conflict/stale/degraded/permission/partial 状态按 §40 覆盖；
- WCAG 2.2 AA、keyboard/focus、reduced motion、desktop/mobile screenshot、visual regression 和独立人工审查通过；
- 不出现虚构指标、客户、推荐语、数据完整性或成功状态。

以上 acceptance 未由独立 evidence 完整证明前，状态只能是“文档阶段 / 目标规范”，不得称为实现完成、测试通过或可发布。
