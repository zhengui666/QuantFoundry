# QuantFoundry Semantic Tool Contracts

`v1-p0.yaml` is the sole field-level Tool-contract source for the staged P0 research flow. Each entry fixes its `name`, `version`, input/output JSON Schema, allowed roles, idempotency class, side-effect class, execution mode, timeout, policy checks, and snapshot requirement.

Version rule: a Tool Call persists the exact `name` + `version`; schema validation always uses that pair. Additive optional fields are a compatible patch within a major version only when `additionalProperties: false` remains satisfied by generated clients. Any required-field, enum, output semantic, permission, side-effect, or execution-mode change creates a new Tool version and retains the previous schema for historical replay. Tool schemas are not prompt examples and an LLM cannot edit registry metadata.

Scope rule: this directory is staged P0/P0.5 only. PRD V1 tools outside `v1-p0.yaml` remain contract-blocked; they must not be invented in prompts, code, fixtures, or tests before their own versioned entry is committed. `run_holdout` is intentionally absent because the Agent role matrix denies it.

Registry authority lock: production authority is the repository-canonical `contracts/tools/v1-p0.yaml` exact 13-entry `name@version` set. Startup MUST load that canonical path, verify its expected content hash, validate the registry document and every entry schema, then compare the exact set (no missing, extra, duplicate, renamed, or version-substituted entry) before accepting traffic. Any failure is fail-closed: no Tool dispatch, Agent resume, or registry fallback. Ordinary environment variables, working-directory overrides, remote locations, or unpinned replacement files MUST NOT replace the canonical production authority. Test-only injection is permitted only through an explicit test harness and must preserve the same authority checks against a declared fixture; it cannot alter production startup behavior or authorize an unregistered Tool. Required negatives cover missing one, extra one, duplicate/name mismatch, version mismatch, invalid registry/entry schema, and invalid Tool input/output instance.

Paper daily scheduling is a deterministic backend P0 service, not an Agent Semantic Tool and not a new HTTP operation. Its executable boundary is PRD §52.1–§52.3, Backend §23.4–§23.4.1, and Test Plan §27.1; it must not be represented by an unversioned Tool entry, prompt-only action, fixture-only schema, or P0.5 scope expansion. `paper_scheduler_evidence.v1` is an internal Audit-linked Artifact contract, never a Tool input/output or EventPayload extension. Current Paper HTTP/UI operations remain `FUTURE_STAGED` until canonical OpenAPI is revised, while the non-HTTP scheduler core remains a P0 blocker and must be independently tested without waiting for that revision.

## UX-001 — D0/D1 control-plane boundary

Status: **TARGET_NORMATIVE / D0_DOCS_ONLY**. The single-Owner, multiple-general-key, DB-only configuration target is normative, but this README does not mutate the current canonical machine contract. **D1 MUST revise and validate canonical OpenAPI plus affected persistence schemas before any production code, migration, fixture, generated client, or implementation test begins.**

The semantic Tool registry remains the exact 13-entry `name@version` set in `v1-p0.yaml`; UX-001 neither adds nor removes a Tool. Authentication, login/logout, Owner sessions, general-access-key create/rotate/revoke/expire, configuration read/write/validate/activate/rollback, Domain DB candidate validation/switch/LKG recovery, root-key access, and configuration-consumer ACK are control-plane operations and **MUST NEVER** become Agent Semantic Tools.

Runtime configuration **MUST NOT** replace, append to, shadow, or weaken the repository-canonical registry path, pinned content hash, exact 13-entry set, JSON Schemas, role allowlists, policy checks, execution mode, timeout contract, idempotency class, or side-effect class. A run may carry the pinned effective-configuration revision/hash and related provenance only in its outer runtime/audit envelope; those references do not alter a Tool request/response schema and do not authorize a Tool absent from `v1-p0.yaml`.

All effective UX-001 configuration selection is resolved from the active revision in Bootstrap Control DB. A catalog entry may bind an exact immutable/versioned domain object whose content authority remains Domain PostgreSQL; the active revision carries that exact object/revision reference, never a second mutable copy or fallback. Environment variables, CLI flags, working-directory files, configuration files, legacy rows, remote URLs, and implicit defaults **MUST NOT** override either database authority or serve as fallback. The root encryption key is the sole bootstrap exception: it is supplied only through OS keychain, TPM, or an explicitly configured external-secret injection boundary; it is not ordinary configuration, is never written to a configuration file, and never enters Tool context.

D1 contract generation MUST prove the exact 13-entry registry is unchanged and add negative cases showing that runtime configuration cannot register, replace, rename, re-version, or bypass any Tool. Exact historical counts elsewhere remain current-baseline evidence until regenerated from the completed D1 canonical contracts; maintainers MUST NOT guess or manually reconcile target counts in D0.
